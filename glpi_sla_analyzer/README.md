# Анализ SLA заявок GLPI по рабочему календарю

Считает чистое время заявок сектора «НСИ» за последние месяцы: понедельник–пятница, 08:30–17:30, обед 13:00–13:45 не входит. Встроенный SLA GLPI для этого не используется.

## Установка

```bash
cd glpi_sla_analyzer
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
copy config.example.json config.json
```

В `config.json` заполните токены. Файл с токенами в git не кладётся.

## Как получить App-Token и User-Token

1. Войдите в GLPI под учётной записью, от имени которой будет идти выгрузка.
2. **Настройка → Общие → API**: включите API, при необходимости ограничьте IP.
3. **Настройка → Общие → API → клиенты API** (или «Добавить клиент API»): создайте клиента и скопируйте **App-Token**.
4. **Профиль пользователя → Удалённый доступ / API**: сгенерируйте **User-Token** (личный ключ). В заголовке он передаётся как `Authorization: user_token …`.
5. Вставьте оба значения в `config.json`. URL API обычно `https://<хост>/apirest.php`.

Учётке нужны права на чтение заявок и журнала (`Ticket`, `Log`). Скрипт ничего не меняет в GLPI.

## Праздники

Список в `work_schedule.holidays`, даты `YYYY-MM-DD`. Эти дни не входят в чистое время, как суббота и воскресенье. Обновите список на новый год. На вкладке «Параметры» — по одной дате в строке.

## Проверка расчёта вручную

Календарь: полезный день = 9 ч − 45 мин = **8.25 ч**. Окна: 08:30–13:00 и 13:45–17:30.

Заявка создана в понедельник 10:00, решена во вторник 14:00, Pending = 0, праздников нет:

- Понедельник: 10:00–13:00 = 3.0 и 13:45–17:30 = 3.75 → **6.75**
- Вторник: 08:30–13:00 = 4.5 и 13:45–14:00 = 0.25 → **4.75**
- Итого: **11.5 часа**

Тот же пример в `tests/test_net_working_hours.py` (`test_known_answer_monday_to_tuesday`). Запуск: `pytest`.

## waiting_duration и solve_delay_stat

| Поле | Что это | Как использует скрипт |
| --- | --- | --- |
| `waiting_duration` | Секунды в статусе «Ожидание» (4), как их накопил GLPI | Переводится в часы и вычитается из рабочего времени |
| `solve_delay_stat` | Время решения уже без ожиданий, по **календарю GLPI** | Только колонка сверки в отчёте |

Если `waiting_duration` пустое или 0, скрипт читает `GET /Ticket/{id}/Log`, суммирует сырые часы между входом в статус 4 и следующим статусом и вычитает их. Если журнала нет — Pending = 0, в лог пишется предупреждение, в отчёте строка помечается «Pending не вычтен».

Восстановленный из журнала Pending — это обычные часы на часах, а не часы вашего календаря. Поле GLPI хранится так же, в секундах астрономического времени.

## Почему цифры не совпадут с отчётом GLPI

Встроенный SLA в GLPI считается по его собственному календарю (по умолчанию 24/7). Этот скрипт считает по вашему: только рабочие дни, с вырезанным обедом 13:00–13:45. Расхождение с отчётами GLPI — нормально.

`solve_delay_stat` уже очищен от Pending и посчитан по календарю GLPI, но не знает про обед 13:00–13:45, поэтому не может заменить результат скрипта. Колонка нужна только чтобы сравнить два разных календаря.

Если `waiting_duration` = 0 и в истории нет статуса «Ожидание», Pending не вычитается — это видно в отчёте.

Часовой пояс в конфиге (`Europe/Minsk`) должен совпадать с часовым поясом сервера GLPI. Даты приходят строкой `YYYY-MM-DD HH:MM:SS` без смещения. Если пояс другой, границы дня и обеда сдвинутся. Пустой `timezone` — локальный пояс машины и предупреждение в логе.

## Фильтр сектора

Ищется категория (поле поиска 7), в названии которой есть «НСИ», либо точный `sector_category_id`. На этом сервере категория «Запрос в НСИ» имеет id **360**. Если в названии категории нет «НСИ», укажите id явно. Группа «НСИ» (2017) сама по себе в фильтр не входит: заявка без такой категории в выборку не попадёт.

В среднее входят только статусы 5 (решена, конец = `solvedate`) и 6 (закрыта, конец = `closedate`). Остальные попадают в список незавершённых и среднее не двигают. Пустой конец или конец раньше начала — строка пропускается, в лог пишется предупреждение.

## CLI

```bash
python analyze.py --config config.json --output report.xlsx
python analyze.py --config config.json --since 90 --verbose
python analyze.py --config config.json --dry-run --output dump.json
python analyze.py --config config.json --fail-on-sla
```

- `--since DAYS` — период в днях вместо месяцев из конфига
- `--dry-run` — только выгрузка поиска, без расчёта часов
- `--verbose` — подробный лог
- `--fail-on-sla` — код 2, если есть хотя бы одно превышение SLA

Коды: **0** успех, **1** ошибка, **2** есть превышения (только с `--fail-on-sla`).

## GUI

```bash
python main_gui.py
```

- **Подключение** — URL, токены, SSL, проверка сессии
- **Параметры** — месяцы, сектор, SLA, часы, обед, праздники, кнопка «Считать»
- **Результаты** — карточки метрик и таблица; превышение SLA подсвечено красным; Excel и CSV
- **Журнал** — ход работы

Расчёт идёт в фоне, окно не блокируется.

## Сервер и cron

Скопируйте каталог на сервер с Python 3.11+, установите зависимости, положите `config.json` рядом (права только у пользователя cron). Часовой пояс ОС может быть любым: расчёт берёт `timezone` из конфига.

Пример cron, каждый понедельник в 07:00, код 2 не считается аварией планировщика:

```cron
0 7 * * 1 cd /opt/glpi_sla_analyzer && /opt/glpi_sla_analyzer/.venv/bin/python analyze.py --config /opt/glpi_sla_analyzer/config.json --output /var/reports/nsi-sla.xlsx >> /var/log/glpi-sla.log 2>&1
```

Для сигнала в мониторинг добавьте `--fail-on-sla` и обрабатывайте код выхода 2 отдельно от 1.

## Сборка exe (PyInstaller)

Из каталога `glpi_sla_analyzer`, после `pip install pyinstaller`:

```bat
pyinstaller --onefile --name glpi-sla-analyze analyze.py
pyinstaller --onefile --windowed --name glpi-sla-gui --hidden-import tzdata main_gui.py
```

Рядом с exe положите `config.json`. Окно — `glpi-sla-gui.exe`, консоль и cron — `glpi-sla-analyze.exe` (без `--windowed`, иначе не будет кода возврата в консоли).
